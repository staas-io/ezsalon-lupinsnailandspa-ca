# Replicate a crawled site into Eleventy

This is a two-step pipeline. Step 1 is a shell script (no AI). Step 2 is the AI agent work this skill describes.

1. **Crawl:** `crawl-site.sh` saves every sitemap URL as a self-contained HTML file with single-file-cli.
2. **Replicate:** the agent turns those HTML snapshots into an Eleventy template in `src/`, builds it to `docs/`, and verifies it.

Reference implementation: `https://lupinsnailandspa.ca/` (Lupins Nails and Spa, Stratford PEI).

## Project layout

```
crawl-site.sh            Step 1 crawler (do not modify unless the crawl is broken)
*.html (repo root)       Crawl output. READ-ONLY reference. Huge (up to 8 MB each, inlined CSS/images/base64).
.eleventy.js             Eleventy config: input src/, output docs/, liquid templates
package.json             Scripts: build, start, serve, dev (bunx @11ty/eleventy)
src/
  _includes/layouts/base.liquid   Shared head, header/nav, footer, script tags
  _data/                          Global data (optional)
  pages/*.html                    One file per page, with front matter
  assets/css|js|images/           Source assets
css/ js/ images/                  Root-level assets also passthrough-copied to docs/
docs/                            BUILD OUTPUT, served by GitHub Pages. Includes CNAME.
_docs/                           Notes and API samples (not published)
CNAME                            Custom domain (a copy must exist in docs/CNAME)
```

Never edit `docs/` by hand. It is regenerated by the build.

## Step 1: Crawl (only if snapshots are missing or stale)

```bash
./crawl-site.sh https://<host>/sitemap.xml        # writes to sites/<host>/ by default
./crawl-site.sh https://<host>/sitemap.xml .      # writes into repo root
```

Requirements: Chromium (`npx playwright install chromium`, or set `CHROME_PATH`), `curl`, `perl`, `npx`.

Known crawl limits, and what they mean for step 2:
- single-file-cli freezes the DOM after JS ran. Interactive behavior is stripped or dead (accordions, menu toggles, sliders, lazy content). Re-create behavior by hand in `src/assets/js/`. Past example: the Home "Our Services" accordion toggle had to be restored manually.
- Content loaded by AJAX appears as a frozen snapshot, or as "Loading...". Find the real API URL in the snapshot and rebuild the dynamic loader instead of copying stale data.
- Internal links are rewritten to site-relative paths (`/about`, not `https://host/about`). Confirm they map to the Eleventy permalinks (trailing slash).
- Page filenames differ from permalinks (`service.html` is the crawl, `/services/` is the page). Keep a mapping.

## Step 2: Replicate (the agent's job)

### 2.1 Review before writing
1. Read `.eleventy.js`, `package.json`, `src/_includes/layouts/base.liquid`, and the existing `src/pages/*.html`.
2. Check git state: `git status --short`. Never discard uncommitted work.
3. Do NOT read crawl HTML whole. Files are megabytes of inlined data. Extract what matters:
   ```bash
   # visible text structure
   grep -oP '<(h[1-6]|title|a|p|li|button|img|section|nav|footer)\b[^>]{0,200}>' index.html | head -200
   # strip base64 and style blobs, then inspect
   perl -0pe 's/data:[^"'"'"')]{100,}/DATA/g; s/<style.*?<\/style>//gs; s/<script.*?<\/script>//gs' index.html > /tmp/index.clean.html
   ```
   Write temp files to `/tmp`, not into the repo.
4. From each page capture: `<title>`, meta description, heading hierarchy, section order, copy text, links (internal and external), image references, forms, embedded maps, and any `data-*` hooks or inline script that fetches from an API.
5. Identify what repeats across pages (header, nav, footer): that goes in the layout. What differs goes in the page file.

### 2.2 Build the template
- **Layout:** one `src/_includes/layouts/base.liquid` with head, SEO meta, nav (active-state ready), `{{ content }}`, footer, scripts. Use the page front matter `title` for `<title>`.
- **Pages:** each `src/pages/<name>.html` starts with:
  ```yaml
  ---
  layout: layouts/base.liquid
  title: Services
  permalink: /services/
  ---
  ```
  Home uses `permalink: /`. Use trailing-slash permalinks so output is `docs/<name>/index.html`.
- **Assets:** CSS in `src/assets/css/`, JS in `src/assets/js/`, images in `src/assets/images/`. Pull images out of base64 into real files (decode `data:image/...;base64,` into `src/assets/images/`) when a snapshot inlined them. Prefer compressed `.webp`/`.jpg`. Do not leave multi-MB inline blobs in templates.
- **Config:** `.eleventy.js` must passthrough-copy every asset directory used by the layout. If the layout references `/css/style.css`, the output must contain `docs/css/style.css`. Keep the layout paths and the passthrough config in agreement. Do not keep two divergent copies of the same file (root `css/` vs `src/assets/css/`). Pick one source of truth.
- **Dynamic content:** keep API URLs in `data-*` attributes on `<body>` (for example `data-services-api`, `data-contact-api`, `data-hours-api`). `src/assets/js/dynamic-content.js` fetches them, handles the response shapes below, and falls back to static text when the API fails.
  - Array of services.
  - `{ services: [...] }`.
  - `{ categories: [{ name, services: [...] }] }`.
  - Wrapped payload `{ json: "<stringified JSON>" }`. Parse the string.
  - Money is in cents (`priceCents`), durations in minutes. Escape all text before `innerHTML`.
  - Samples live in `_docs/services-api-sample.json` and `docs/settings-api-sample.json`.
- **Behavior:** nav toggle, accordions, and similar go in `src/assets/js/main.js`. Use plain JS, no framework, unless the original needs one.
- **Escape Liquid:** page text containing `{{`, `{%` must be wrapped in `{% raw %}...{% endraw %}`.
- **Accessibility and SEO:** one `<h1>` per page, `alt` on images, `lang`, viewport meta, meta description, canonical links only if the domain is known, `rel="noopener noreferrer"` on `target="_blank"`.
- Keep scope tight. Replicate what the original has. Do not invent new sections, copy, or features.

### 2.3 Build and release
```bash
bun install            # or npm install
bun run build          # = bunx @11ty/eleventy, writes docs/
bun run serve          # = bunx serve docs  (static check of the release)
bun run dev            # eleventy --serve --port=9001 (live reload while editing)
```
Release rules:
- `docs/` is the release. Commit it together with the `src/` change that produced it.
- `docs/CNAME` must still exist after a build. Eleventy does not delete extra files, but if the dir is wiped, restore it from the root `CNAME` (current value `lupinsnailandspa.staas.io`). Add a passthrough for `CNAME` if it keeps going missing.
- A clean rebuild with no source changes must produce no `git diff` in `docs/`. If it does, find the non-determinism before committing.
- Only commit or push when the user asks.

### 2.4 Parity checklist (do for every page)
- Same page title, headings, copy, and section order as the crawl.
- Every nav and footer link resolves to a built page or a valid external URL. No `404`, no links to the old host unless intended.
- Every image loads. No leftover `data:` blobs above ~10 KB in `src/`.
- Interactive pieces work: mobile nav toggle, accordions, booking link, tel/mailto links.
- Dynamic blocks (services, hours, contact) render from the API and still show a sensible fallback offline.
- No console errors, no failed network requests besides the documented third-party APIs.

## Testing with `/agent-browser`

Invoke the `agent-browser` skill to verify the built site as a user would. Serve `docs/` first (`bun run serve`, or `bunx serve docs -l 3000`).

Run this loop per page, desktop (1280 wide) and mobile (375 wide):
1. Open `http://localhost:3000/<path>/`.
2. Take a screenshot. Open the original (`https://lupinsnailandspa.ca/<path>` or the crawl snapshot via a second `serve`) and screenshot it too. Compare layout, spacing, fonts, colors, images.
3. Read the console and network logs. Zero JS errors. Zero 404s for local assets.
4. Click every nav item, the mobile menu toggle, each accordion, the Booking button, footer social links, `tel:` and `mailto:` links. Confirm the result.
5. Confirm dynamic content: `#services-list` populated, `#footer-address`, `#footer-phone`, `#footer-email`, `#footer-hours` no longer say "Loading...". Then block the API and confirm the fallback.
6. Fill and submit the contact form if the original has one (check the target and validation).

Record each failure as: page, viewport, step, expected, actual. Fix in `src/`, rebuild, retest. Do not patch `docs/`.

## Design review with `/impeccable`

### Install (one time, per project)
```bash
npx impeccable install --yes --project --providers=claude-code
```
This writes `.claude/skills/impeccable/` (with a native `impeccable` engine binary), `.claude/agents/`, and hook manifests into `.claude/`. The hooks make detection run automatically in the harness. It needs network and changes project config, so tell the user first. Afterwards run `/impeccable init` in the agent chat once (a design-context interview that creates `PRODUCT.md`/`DESIGN.md` context). Commit `.claude/` only if the user wants it shared.

There is no built-in auto-fix mode. Impeccable detects; the agent applies the fixes. Treat "auto detect and auto fix" as this loop: detect, fix in `src/`, rebuild, re-detect, until only accepted findings remain.

### Detect
Serve the release first (`bunx serve docs -l 3000`, started with `nohup ... &`), then scan.
```bash
npx -y impeccable detect http://localhost:3000/<path>/     # full check: parsed page, contrast, headings, line length
npx -y impeccable detect docs                              # regex-only on files: undercounts, not a clean bill
npx -y impeccable detect <url> --viewport 390x844          # mobile pass
npx -y impeccable detect <url> --json                      # machine-readable
npx -y impeccable detect --list-rules                      # rule catalog
```
Always scan every page as a served URL (`/`, `/about/`, `/services/`, `/coupons/`, `/gallery/`, `/policy/`, `/contact/`, `/blog/`). File scans skip element rules (tiny-text, low-contrast). `detect` exits non-zero when it finds anything, so do not chain it after `set -e`.

### Fix and re-detect
1. Edit `src/` only (and the duplicate root `css/`, `js/` if they still exist: copy from `src/assets/`). Never edit `docs/`.
2. `bun run build`.
3. Re-run `detect` on every page. Repeat until clean or the remainder is on the accepted list below.
4. Then rerun the `agent-browser` loop for regressions.

### Findings fixed on lupinsnailandspa.ca (reference)
| Finding | Cause | Fix |
|---|---|---|
| `low-contrast` 2.1:1, `#d3ad32` on white | `.service-item__price` gold text | color to `#8a6d00` (about 4.9:1). Gold buttons and footer bar with black text are fine. |
| `skipped-heading` h2 to h4 (Home), h1 to h4 (Services) | `dynamic-content.js` always emitted `<h4>` | Renderer reads `data-heading-level` from `#services-list`. Home uses `3`, Services uses `2`. |
| `line-length` about 106 to 108 chars | intro paragraphs `max-width: 800px` | `max-width: 68ch` on `index.html` intro and `about.html` text block |

### Accepted, not fixed
- `ai-color-palette` purple `#8000b6` on headings, every page. It is the original brand colour. Fidelity wins.
- `side-tab` `border-left: 4px solid #8000b6` on `.service-item`. Part of the original card style. Revisit only if the user asks.
- `straggler` advisory on About ("environment." alone on the last line). Cosmetic.

### Rules for applying feedback
- Fidelity to the original wins over taste. This is replication. Apply fixes that make the replica closer to, or no worse than, the original, plus real defects (contrast, broken responsive layout, tap targets under 44 px, missing focus states, heading order).
- Present larger visual redesigns to the user as options. Do not apply them silently.
- Other `/impeccable` commands (`/audit`, `/critique`, `/polish`, `/typeset`, `/layout`, `/adapt`, `/harden`) are for subjective review. Run them only when the user asks, and show the proposed changes before applying.
- After any change, rebuild, re-detect, and rerun the `agent-browser` loop.

## Done criteria
- `bun run build` exits 0 with no template errors.
- `docs/` contains an `index.html` and a `<page>/index.html` for each page, plus `css/`, `js/`, images, and `CNAME`.
- Parity checklist passes on desktop and mobile through `agent-browser`.
- `impeccable detect` on every served page shows only the accepted findings, each listed with a reason.
- Rebuild is idempotent (`git status` shows no unexpected `docs/` drift).
- Final report to the user lists: pages built, files changed, test evidence (screenshots or log summaries), and open issues.

## Pitfalls
- Reading a whole crawl file blows the context window. Always filter first.
- Editing `docs/` directly: the next build overwrites it.
- Absolute `/css/...` paths break when the site is served from a subpath. This site uses a custom domain at the root, so absolute paths are fine. If that changes, use Eleventy's `url` filter and `pathPrefix`.
- Duplicate asset trees (`css/` and `src/assets/css/`) drift apart. Keep one.
- The crawl's frozen "Loading..." placeholders are not real content.
- Copyright year and footer text come from the original. Confirm before changing them.
- `pkill -f "serve docs"` inside a Bash call matches its own command line and kills the shell (exit 144). Start the server with `nohup bunx serve docs -l 3000 >/tmp/serve.log 2>&1 &` and stop it by PID or a pattern that does not appear in your own command.
- Server must be up before URL scans: `ERR_CONNECTION_REFUSED` means it died. Restart it.
- `impeccable detect` file scans (`docs/`) report only regex rules. Do not call a site clean from them.
- Fixing a shared renderer (`dynamic-content.js`) needs per-page parameters (`data-*` attributes), not one hard-coded value, when pages sit at different heading depths.
